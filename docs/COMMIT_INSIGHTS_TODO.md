## 一、目标与边界

### 目标

在项目详情页的「Git 提交记录」面板内，新增一块**提交构成分析**，回答两个问题：

1. **分类计数** —— 这个仓库的提交按类型怎么分布；
2. **主要发力点在哪里** —— 发力点在什么时间、集中在哪类工作上。

关键判断：现有前端已有 `commitTypes()` 做类型计数，但它只统计 `/commits` 已加载的 **≤200 条**，结构上回答不了"发力点"。
因此本需求的核心不是"再画一个图"，而是**把统计口径从「最近 200 条」提到「全量」**。

### 硬边界（逐条编号，后续每一步都不得违反）

| 编号 | 边界 |
|---|---|
| **B1** | **全程只读 git**：只执行 `git log` 等只读命令，绝不写入被解析的项目仓库（不 commit / 不 add / 不 stash / 不 checkout）。 |
| **B2** | **不改动现有接口语义**：`GET /commits`、`GET /heatmap` 的参数与返回结构保持不变；新能力一律走新端点。 |
| **B3** | **前端零新增依赖**：沿用本地 vendored Vue3，无构建步骤、无 CDN、不引入图表库；图表用原生 div/CSS 实现。 |
| **B4** | **统计口径以后端为唯一真源**：前端筛选 chips 的分类计数优先取后端结果，本地计算仅作 fallback，避免两套分类器长期漂移。 |
| **B5** | **不得假设提交信息规范**：必须能处理无前缀、中文、自造前缀（如 `design:` / `security:`）的提交，不能让它们全落进 other。 |
| **B6** | **失败必须降级**：git 命令超时 / 非 git 目录 / 路径丢失时，只有该分析块显示降级文案，`#sec-commits` 其它内容与页面其它面板照常。 |
| **B7** | **不假装全量**：受样本上限截断时必须在界面上如实标注"基于最近 N 次提交"。 |
| **B8** | **样式只用既有体系**：复用现有 CSS 变量（`--s-*` / `--r-*` / `--panel-2` / `--border` / `--ok` / `--danger` 等）与 `.ct-*` 配色，不新增色值体系。 |
| **B9** | **统计只算条数，不混算工作量**：L1/L2 是"提交次数"口径，代码量维度只作为已有样本的补充，且必须写明样本范围。 |

## 二、设计要点

1. **数据源选型**：只用 `git log --pretty=format:<日期>\\x1f<subject>`，**不带 `--numstat` / diff**。
   与已上线的 `collect_heatmap()` 同一路线（已验证毫秒级），不引入新依赖。
2. **分类三级口径**（按优先级）：
   1. 白名单 12 类：`feat/fix/docs/style/refactor/perf/test/chore/build/ci/revert/merge`；
   2. **未登记前缀以前缀名成类**（`design:` / `security:` / `init:` 各自成类，最多 6 个，其余并入"其他"）；
   3. 无前缀 → 关键词弱分类，结果标注"推断"，**默认不进主图**。
3. **merge 处理**：默认用 git 自身的 `--no-merges` 排除（语义准确，不是靠 subject 猜）。
4. **发力点三层**：L1 类型分布（全量）→ **L2 类型 × 月份堆叠（全量，看发力点何时转移）** → L3 代码量（沿用已有样本，标注范围）。
5. **规模护栏**：`--max-count` 上限 + 返回 `truncated` 标志，前端如实提示。
6. **UI 落位**：`#sec-commits` 面板内、月柱状图下方、类型筛选 chips 上方，复用 `.month-bars` / `.mb-*` 结构与 `.ct-*` 配色。

## 四、进度

> 每完成一项追加一行。重点写「为什么这么改」，而不只是「改了什么」。

- **2026-09-19 · 建立文档**：先把边界与子功能清单定下来再动代码，避免实现过程中扩大改动面（尤其 B2「不改现有接口」与 B8「不新增色值体系」最容易在写 UI 时被悄悄突破）。
- **2026-09-19 · S1 完成**：`gitinfo.collect_commit_stats()` + `config.COMMIT_STATS_MAX / COMMIT_STATS_TYPE_LIMIT`。
  - **偏离原方案 S3 的一处**：原计划把"分类白名单"也放 `config.py`，实际放在了 `gitinfo.py` 里。
    理由：白名单与关键词规则是**行为**（跟正则、聚合逻辑强耦合、要一起读才看得懂），不是可调参数；
    `config.py` 只放真正的规模护栏（上限 20000）与展示条数上限（8），与既有的 `STATS_MAX_FILES` 等同族。已在文档与本表记录。
  - **`--no-merges` 而非 subject 匹配**：合并提交用 git 自己的 `--no-merges`（按父提交数判定）排除，比"看 subject 是不是以 Merge 开头"准确；
    `merge` 仍留在白名单里，用于**单亲提交**但写了 `merge:` 前缀的情况。
  - **未登记前缀成类**：本仓库实测有 `design:`(3) / `security:`(2) / `init:`(1) 共 6 条不在白名单内，
    若不做这一级会被埋进 other，直接毁掉"发力点"结论的可信度——这是本功能成败的第一决定项。
  - **数值守恒**：`types` 各计数之和 == `scanned`，`pct` 由后端一次算好，避免前后端两处取整口径不一致。
  - **种类排序口径（自检后补明确）**：各种类按 `提交数倒序 → 同数时白名单类型优先 → 名称字典序` 排序，取前
    `TYPE_LIMIT - 1` 个作为具名行，其余并入「其他」。加"白名单优先"这一档是因为纯按 count 排时，
    一个自造前缀可能把标准类型挤出榜单，而这与「未登记前缀要限流」的本意相悖。
  - **自检（临时探针，跑完即删）**：分类器 8 项单元行为 + 本仓库/scope=year/混合仓库/自造前缀仓库/空仓库/
    非 git 目录/不存在路径/截断 共 8 类样本，逐个校验守恒（`Σtypes == scanned`、`Σmonths.total == scanned`、
    每月分段之和 == 该月 total）与结构约束，**全部通过（0 失败）**。
  - **一次真·假警报，已查清**：探针首轮报 "下 `design/security/init` 未被埋进 other" 失败。
    排查后确认是**探针的预期写错**，不是实现错：`TYPE_LIMIT=8` 意味着最多 7 个具名行 + 「其他」，
    本仓库 11 个原始种类塞不下，`design`(3) 已经是能挤进榜的最后一名，`security`(2)/`init`(1) 按规则本就该并入「其他」。
    顺带用 `git log --date=short` 复核了服务输出（121 提交 / 11 个活跃日 / 2026-08-29 起），与 git 逐位一致。
    —— 教训记录在案：**自检跑红时先怀疑夹具**，这次又是夹具。
- **2026-09-19 · S2 完成**：新增 `GET /{project_id}/commit-stats`。
  - 参数用 `Query` 做白名单约束（`scope` 只允许 `all|year`、`max_commits` 限定 100~50000），非法值交给 FastAPI 直接 422，不自己写校验；
    `scope` 用 `pattern` 而不是 `Literal`，这样不必为此新增 `typing` 导入。
  - 前置校验沿用 `_get_row_or_404` + `os.path.isdir`（与 `/commits`、`/heatmap` 完全一致），路径丢失时行为统一。
  - 端点写成同步函数（`def` 而非 `async def`），与既有 git 端点一致：FastAPI 会把它丢线程池，git 子进程阻塞不会卡住事件循环。
  - **自检（临时探针）**：22 项全过。除守恒外，专门验证了**不回归**——`/commits` 与 `/heatmap` 的字段结构不变、
    `max_commits` 的上下界与非法 `scope` 都返回 422、不存在的项目 404、非 git 项目 200 + `is_repo=False` 降级。
  - **测试环境两处坑（下轮沿用）**：① 本机 8300 被**已安装的 Tracelight**（数据目录在 `%LOCALAPPDATA%\Tracelight`）占着，
    直接跑冒烟测试会写到用户真实档案库，必须另起端口；② 沙箱设了 `http_proxy=127.0.0.1:6141`，
    非 8300 端口会被代理挡成 **502 Bad Gateway**（看起来像服务没起来），需在脚本里 `no_proxy=127.0.0.1,localhost` 直连。

## 五、本轮不做

| 项 | 原因 |
|---|---|
| 目录维度发力点（按 `--numstat` 聚合"改得最多的目录"） | 比类型分布更贴近"改了哪个模块"，但需要全量 `--numstat`，成本显著高于本方案（本方案的毫秒级前提是**不带 diff**）。要做得先限定 `--since` 与条数上限，属于独立课题，不适合塞进本轮。 |
| L3 代码量改成全量统计 | 同上：全量增删行数需要逐提交 diff。本轮沿用 `/commits` 已加载样本，并在 UI 写明样本范围（B9）。 |
| 弱分类（关键词猜测类型）进主图 | 误判会直接污染"发力点"结论的可信度，代价大于收益。本轮只在返回结构里保留计数、界面不展示。 |
| 类型下钻联动时间线 | 时间线上方**已有类型筛选 chips** 实现同样能力，再加一个入口属于重复入口（同类重复入口在本项目历史上已被指出过两次）。 |
| 在首页仪表盘做全库提交分析 | 需求原文限定在"提交记录分析"，且全库汇总需要遍历所有仓库，代价远大于单个项目；不在本次范围内。 |

## 七、验收清单（需真机确认）

沙箱里只能验证到"接口返回正确 + DOM 里出现了这些元素"，**视觉效果与交互需要在本机浏览器/桌面版确认**：

1. **看得到吗** —— 打开任一 git 项目详情页，滚到「Git 提交记录」面板，在"每月提交量"柱状图**下方**应看到「提交构成分析」块；若该项目不是 git 仓库，这一块应完全不存在（不留空壳）。
2. **数字对得上吗** —— 块头"全量 N 次提交"里的 N，应与面板标题里的"共 N 次"一致（同一仓库同一口径）。
3. **堆叠柱读得对吗** —— 把鼠标停在任意一根月柱上，提示应显示该月的总次数；柱子高度应随该月提交量变化，最近一个月（当前月）的标签应与其它月份有可见区别（沿用 `.mb-col.current` 的高亮）。
4. **chips 有没有变** —— 类型筛选 chips 上的数字，应与左侧类型分布条的数字**完全一致**（这是 B4 生效的证据）。若不一致说明前端退回了本地计算。
5. **暗色主题下能看吗** —— 切到暗色主题，堆叠柱与分布条不应出现"黑底黑条"或颜色糊在一起。
6. **窄窗口会不会溢出** —— 把窗口拉窄，两栏（类型分布 / 类型×月份）应能换行而不是横向撑开页面。
7. **降级文案** —— 随便找个非 git 的普通文件夹录进来，进详情页后该块不应出现，且面板其余部分（时间线空态提示）正常。

## 八、已知边界

1. **条数 ≠ 工作量**：`feat: 完成整个模块`（1 条）与 20 条 `fix: typo` 在条数上后者占优。L1/L2 都是"提交次数"口径，工作量只能参考 L3 且受样本限制。
2. **弱分类不显示**：无 Conventional 前缀的提交在界面上会落到"其他"，不会被猜成某个类型。
3. **翻译差异**：git 的语言环境若被设置为非英文，`--no-merges` 这类参数不受影响（是参数不是输出文本），但提交 subject 可能为任意语言，分类只看前缀与关键词，不看语言。
4. **截断**：超过 `COMMIT_STATS_MAX`（20000）次提交的仓库，统计基于最近 20000 条，界面上会如实标注。
5. **时区**：月份归集用提交自带的 `%cI`（含时区偏移）取前 7 位，跨时区协作的仓库可能出现个别提交落在相邻月份——与 GitHub 贡献图的行为一致，不额外处理。
